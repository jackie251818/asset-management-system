# 发布与服务器文件同步规范（AI 交接必读）

> **核心原则：本地仓库是唯一事实源，任何时刻都应满足「仓库 = 生产 192.168.40.247」。**
> 每完成一次改动（热上传、发版、或直接在生产服务器上修改过任何文件），收尾动作必须运行一次 [../server/deploy/sync-from-prod.ps1](../server/deploy/sync-from-prod.ps1) 审计同步，发现漂移立即回灌进仓库。
>
> 最后更新：2026-09-13

---

## 一、为什么需要（背景）

- 生产服务器上的文件会因**热上传**（前端 pscp、服务端文件+restart）和**应急直接修改**而变动；仓库不同步就会变成"生产才是最新代码"，后续任何人/AI 基于旧仓库开发都会出问题。
- App/EXE 的**发布二进制**在生产 `/opt/asset-server/downloads/` 用**固定文件名覆盖**，旧版本字节发版即消失；紧急回滚需要旧版实物，因此每次发版产物必须在本地 `releases/` 归档（git 忽略，仅本机留存）。
- App 覆盖安装依赖**包名与签名连续**，签名密钥一旦丢失/更换，已装客户端全部无法应用内更新——这是发布同步中最高的硬约束。

## 二、同步方向矩阵（什么场景做什么）

| 场景 | 数据流向 | 收尾动作 |
|---|---|---|
| 改前端（index.html / js/*.js / styles.css 等） | 仓库 → 生产 | pscp 热上传（**必须 bump index.html 中对应 `<script>/<link>` 的 `?v=` 版本号**）；收尾跑 sync-from-prod.ps1 确认 |
| 改服务端（server/src/**、backup.js 等） | 仓库 → 生产 | pscp 上传 + `sudo systemctl restart asset-server`；收尾跑审计 |
| 改部署文件（server/deploy/**） | 仓库 → 生产 | pscp 上传到 `server/deploy/`；收尾跑审计 |
| **应急直接在生产上改了文件** | **生产 → 仓库** | **立即**跑 sync-from-prod.ps1 → 对每个 DRIFT 确认哪边为准 → 回灌进仓库 → git 提交 |
| 发 App 新版（APK） | 仓库 → 生产 → releases/ | 按 [手机App发布更新流程.md](手机App发布更新流程.md) 8 步；上传验证后**归档产物到 `releases/app/<versionName>-vc<versionCode>/`**；在流程文档「发布记录」表加一行；收尾跑审计 |
| 发 EXE 新版 | 仓库 → 生产 → releases/ | 按 [EXE客户端发布更新流程.md](EXE客户端发布更新流程.md) 9 步；归档到 `releases/exe/<version>/`；更新发布记录；收尾跑审计 |

## 三、一键同步审计：sync-from-prod.ps1

```powershell
powershell -ExecutionPolicy Bypass -File server\deploy\sync-from-prod.ps1
# 可选: -SkipJson 跳过 JSON 归档; -RemoteHost / -Password 覆盖默认连接
```

脚本自动完成四件事：

1. 获取生产 49+ 个文件（静态前端 / js / server 源码 / deploy 关键文件 / downloads）的 SHA256；
2. 与本地仓库逐文件比对 → 输出 `[OK]` / `[KNOWN]`（预期差异白名单）/ `[DRIFT]`（需处理）；
3. 拉回生产 `apk-update.json` / `client-update.json`，按版本自动归档到 `releases/`，并校验归档二进制哈希 == JSON `sha256`；
4. 结论区列出全部漂移文件与回灌 pscp 命令模板。

**如何处理 DRIFT**：先判断哪边新（生产热上传的一定比仓库新 → 回灌；仓库改了还没上传 → 上传）→ 回灌/上传后**复跑脚本直到 0 漂移** → git 提交。

**预期差异白名单**维护在脚本顶部 `$KnownDiff`（当前 2 项：`build-info.json` 构建信息本地随构建更新、`server/backup.js` 注释路径差异）。新出现"确认以本地为准且长期不同"的文件时，在此登记并注明原因，不要让它一直挂着 DRIFT。

## 四、App 更新的包名与签名（硬约束）

| 项 | 规则 | 违反后果 |
|---|---|---|
| 包名 | `com.assetmanagement.mobile`（`mobile-app-rn/android/app/build.gradle` 的 `applicationId`）**禁止修改** | 无法覆盖安装，只能卸载重装丢数据 |
| 签名 | 永远用 `mobile-app-rn/android/app/debug.keystore`，**勿删勿换勿重新生成** | 换签名 = 全部已装客户端无法应用内更新 |
| versionCode | 每次发版 **+1**（整数，唯一更新判定依据） | 不递增客户端不弹更新 |
| 更新 JSON | UTF-8 **无 BOM**；与 APK **成对同步**上传 | 乱码 / 下载到不匹配的包 |

**签名连续性验证**（每次发版前 + 发现异常时；build-tools 不支持中文路径，先复制到 `C:\Windows\Temp\` 再验）：

```powershell
Copy-Item "<APK路径>" C:\Windows\Temp\check.apk -Force
& "C:\Android\Sdk\build-tools\34.0.0\apksigner.bat" verify --print-certs C:\Windows\Temp\check.apk   # 应为 CN=Android Debug
& "C:\Android\Sdk\build-tools\34.0.0\aapt.exe" dump badging C:\Windows\Temp\check.apk | findstr package   # 核对包名/versionCode
Remove-Item C:\Windows\Temp\check.apk -Force
```

**归档即证据**：`releases/app/` 里归档的 APK 是"上一个已发布签名"的实物。新构建的签名指纹若与归档不一致（apksigner 输出不同），**禁止发布**，先查 keystore 是否被换。`releases/README.md` 有归档时机、目录约定与当前台账。

## 五、AI 交接检查单（每次改动完成时逐项过）

- [ ] 本次改动有没有落过生产服务器（热上传 / 直接修改 / 发版）？
  - 有 → 运行 `server\deploy\sync-from-prod.ps1`，处理到 0 DRIFT
- [ ] 发过新版 App/EXE？
  - 是 → `releases/` 归档产物 + JSON（哈希校验通过）→ 对应流程文档「发布记录」表加一行
- [ ] 前端改动 → index.html 的 `?v=` 版本号 bump 了吗？
- [ ] 服务端改动 → `systemctl restart asset-server` 了吗？
- [ ] `git status` 已说明（提交需用户确认）
- [ ] 有新的"长期预期差异"？→ 登记 `$KnownDiff` 白名单
